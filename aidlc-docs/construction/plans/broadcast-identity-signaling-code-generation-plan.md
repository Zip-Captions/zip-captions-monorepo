# Code Generation Plan: Broadcast Identity + Signaling (Unit 3)

**Unit**: broadcast-identity-signaling | **Prior stage**: Infrastructure Design, approved 2026-09-30
**Stories**: S-11, S-13 (gated by SR-02)
**Project type**: Brownfield (Flutter monorepo) — modify/extend existing packages in place, never create `_new`/`_modified` duplicates.

## Unit Context

- **Package placement** (fixed at NFR Design `logical-components.md`): `zip_supabase` gets the SQL migration only (no Dart — it's TS/Deno+SQL per `AGENTS.md`). All Dart types/implementations live in `zip_core`, mirroring Unit 2's `SupabaseAuthService` precedent.
- **Dependencies**: reuses Unit 2's `supabaseClientProvider` as-is (no change to it). No dependency on Unit 5 (`ViewerAdmission`, message-type authorization) or Unit 7 (viewer UI) — both explicitly out of scope here.
- **Clarification resolved during planning** (not previously written down, needed before any code can be correct): SR-02 §3 states broadcast IDs are "stored and compared case-sensitively as generated" (the Crockford alphabet is uppercase) but "displayed lowercase to broadcasters." For a viewer who pastes a lowercase-displayed code or link, `resolve_broadcast_id`'s case-sensitive comparison would otherwise never match. **Decision**: `BroadcastId.parse`/`tryParse` validate the Crockford alphabet case-insensitively and always normalize `.value` to canonical uppercase — the single source of truth sent to the RPC and compared against stored rows. Lowercase display (`k7m9x2`-style) is a presentation-only concern (e.g. `.value.toLowerCase()` at the UI call site in Unit 6/7), never stored on the value object itself. This keeps `testable-properties.md`'s round-trip property intact (its generator produces canonical-case strings) while making real viewer input actually resolve.
