# Business Logic Model — Broadcast Identity + Signaling

## F-BIS-1: Get or Create My Broadcast ID (S-11 AC1, AC2)

1. `BroadcastIdentityRepository.getOrCreateMine()` is called (only ever from an
   authenticated context — `AuthState.SignedIn`; throws if signed out, per the fixed
   interface).
2. `SupabaseBroadcastIdentityRepository` calls `get_or_create_my_broadcast_id()`
   (SR-02 §3).
3. The Postgres function checks for an existing row for `auth.uid()` first — a second
   call from the same broadcaster (e.g. starting a later broadcast) always returns the
   same code, never allocates a new one (S-11 AC2, "the same broadcast ID is reused").
4. If none exists, it generates a candidate 6-character code and attempts insert,
   retrying on a unique-constraint collision (bounded attempts) — this satisfies S-11
   AC3 ("two broadcasters requesting IDs concurrently" each get a distinct code; the
   `owner_id` unique constraint additionally prevents a race from ever producing two
   rows for the same broadcaster).
5. Returns the `BroadcastId`, wrapped from the raw string via `BroadcastId.parse`
   (never `tryParse` here — a value freshly generated by our own Postgres function is
   always valid by construction; a parse failure at this point would indicate a real
   bug, not bad user input, so it's allowed to throw).

## F-BIS-2: Anonymous Resolution (S-19/Unit 7's dependency, FR-2.5, FR-2.7)

1. `BroadcastLink.parseInput(rawInput)` — invalid input returns `null` with no network
   call (F-BIS at the boundary, shared with Unit 7's `ViewerSessionNotifier`).
2. `BroadcastResolver.resolve(id)` calls `resolve_broadcast_id` (SR-02 §2).
   - `false` → `NotFound`.
   - `false`-equivalent-via-429 → `RateLimited` (once Kong's rate limit exists).
3. On `true`, `BroadcastResolver` opens `status:{broadcast_id}` (a `private: true`
   Realtime channel, SR-02 §4) and inspects current presence.
   - The channel join / presence read completes and finds no presence → `Offline`
     (FR-2.7 — "not currently broadcasting," a confirmed result).
   - Presence present, carrying `sessionId`/`sessionName` → `Live(sessionId,
     sessionName)`.
   - The channel join / presence read itself errors or times out (a transient
     Realtime/network problem, distinct from a clean "joined, found nothing") →
     `ResolutionFailed` (added at NFR Design, `domain-entities.md`) — never `Offline`,
     since that would misreport "we couldn't check" as "confirmed not broadcasting."
4. The resolver does not need to *stay* subscribed to `status:{broadcast_id}` to
   satisfy a one-shot `resolve()` call — a single presence read suffices; a *live*
   view (e.g. the viewer screen updating in real time after joining) uses
   `StatusChannel.watch()` separately (F-BIS-3), not this resolution path.

## F-BIS-3: Broadcaster Publishes Live/Offline Status (S-11, FR-6.2, FR-6.5)

1. `SignalingService.statusChannel(id)` returns a `StatusChannel` bound to
   `status:{broadcast_id}`, created `private: true`.
2. `StatusChannel.publishLive(sessionId, sessionName)` — enforced server-side (SR-02
   §4's broadcaster-only `INSERT` policy) as belonging only to the owning broadcaster;
   an attempt from any other `auth.uid()` is rejected by Postgres RLS before it ever
   reaches other subscribers.
3. `StatusChannel.publishOffline()` (FR-6.5, ending a broadcast) — same
   authorization.
4. `StatusChannel.watch()` — any subscriber (broadcaster's own dashboard, or a
   resolver holding a live subscription) receives live/offline transitions, including
   the presence-expiry-driven offline transition when the broadcaster disappears
   without a clean end (FR-6.6, Spike 2.1's 60s `presenceTimeout`).

## F-BIS-4: Session Signaling Open/Send/Receive (S-13, FR-3.1–FR-3.4)

1. `SignalingService.sessionChannel(sessionId, role)` returns a `SessionSignalingChannel`
   bound to `signaling:{session_id}`, created `private: true`, role-scoped
   (`SignalingRole.broadcaster` or `.viewer` — this is a client-side parameter that
   determines which local behaviors are exercised, not itself an RLS input; RLS
   authorization is by `auth.uid()`/anonymity, not by a client-asserted role string).
2. `open()` establishes the channel subscription.
3. `send(message)` — encodes via `SignalingCodec.encode` and publishes as a `broadcast`
   payload. RLS's channel-level `INSERT` policy (SR-02 §4) permits any peer to publish;
   *message-type* restriction (only the broadcaster may send `JoinAccepted`/
   `JoinRejected`/`BroadcastEnded`) is enforced by the orchestrating transport layer
   (Unit 5), per SR-02 §4's documented defense-in-depth split — this unit's
   responsibility ends at "the channel accepted the publish and validated its shape,"
   not "this specific sender was allowed to send this specific message type."
4. `messages` stream — every inbound payload passes through `SignalingCodec.decode`
   first; a `null` result (malformed/unknown-type/unsupported-version/oversized) is
   dropped silently, never surfaced as an error and never crashes the app (FR-3.2,
   `business-rules.md`).
5. `presence` stream — broadcaster-role only (SR-02 §4's presence `SELECT` policy);
   used for the viewer-count/capacity signal Unit 5 consumes.
6. `close()` — unsubscribes; does not itself publish `Leave`/`BroadcastEnded` (that's
   the caller's responsibility, at the point they decide to leave/end, not an implicit
   side effect of closing the local subscription).

## F-BIS-5: Malformed or Adversarial Signaling Input (FR-3.2, Rule: never crash)

Covered structurally by F-BIS-4 step 4 — `SignalingCodec.decode`'s `null`-on-invalid
contract is the single chokepoint every inbound message passes through, mirroring Unit
2's single-exception-mapping-chokepoint pattern (SR-01 Rule 9) for a parallel reason:
one reviewable place to audit rather than scattered validation.
