# NFR Requirements — Unit 3: Output Targets

## FD Business Rule Updates

Two answers from the NFR assessment supersede FD decisions and must be reflected in the business rules:

| Rule | Original | Updated |
|------|----------|---------|
| BR-U3-09 | Flush to repository every 30 seconds; final flush on stopped | **Superseded by REL-U3.3** — immediate flush per final segment; 30s timer removed |
| (new) | `OnScreenCaptionTarget` emits on every buffer change | **PERF-U3.1** — stream emissions debounced to ≤1 per ~50ms |

---

## 1. Performance

### PERF-U3.1: OnScreenCaptionTarget — Stream Emission Debounce

`OnScreenCaptionTarget.onVisibleCaptionsChanged` must debounce stream emissions to at most **one emission per 50ms**. STT engines can produce interim results at high frequency (multiple per second); without debouncing, the caption widget would rebuild excessively, wasting CPU and causing jank.

**Mechanism**: The `_controller.add()` call is wrapped in a debounce timer (50ms). Internal state (`_buffer`, `_currentInterim`) is updated synchronously on every `onCaptionEvent()` call. Only the notification to downstream listeners is throttled. The most recent state is always emitted — no intermediate state is dropped permanently, only coalesced.

**Verification**: A test publishes 10 `SttResultEvent`s within 10ms and asserts the stream emits exactly 1–2 times (not 10). A separate test asserts that if events arrive 60ms apart, each produces an emission.

---

### PERF-U3.2: FTS5 Search Latency ≤ 500ms

`TranscriptRepository.search()` must complete within **500ms** against a database containing up to 1,000 sessions and 100,000 segments, measured using an in-memory drift database seeded with fixture data.

**Scope**: This applies to the FTS5 `MATCH` + `JOIN` + grouping pipeline defined in the business logic model. The 50-result limit (BR-U3-15) and the `porter unicode61` tokenizer (BR-U3-16) are design constraints that keep this achievable.

**Verification**: A test seeds an in-memory drift database with 1,000 sessions and 100 segments each, runs a representative search query, and asserts the result is returned within 500ms. This is a logged warning threshold, not a CI gate — if a future regression occurs it is surfaced, not a hard failure.

---

### PERF-U3.3: BrowserSourceServer — SSE Client Cap at 5

`BrowserSourceServer` accepts at most **5 simultaneous SSE clients**. A sixth connection attempt to `GET /captions` receives `503 Service Unavailable` with body `{"error":"max_clients_exceeded"}`.

**Rationale**: In practice, users connect one OBS browser source. A cap of 5 allows for accidental duplicate tabs and debugging tools while preventing runaway resource use.

**Verification**: Test that the 5th connection succeeds and the 6th returns 503. Test that when a client disconnects, the slot is freed and a new connection is accepted.

---

## 2. Security

### SEC-U3.1: No Transcript Text in Logs — All Unit 3 Components (SECURITY-03)

Extends BR-U3-36 to an NFR-level enforcement requirement. No Unit 3 component may include any of the following in log output, error messages, or exception messages:

- `SttResult.text`
- `TranscriptSegment.text`
- `CaptionDisplayEntry.text`
- `TranscriptSession.title`
- Any SSE payload `text` field

**Permitted in logs**: `sessionId`, `segmentId`, `entryId`, `sourceId`, `targetId`, byte counts, event types, connection state names, port numbers, error types, stack traces.

**Verification**: Code review of all `log()` call sites in Unit 3 components. No test can automate this comprehensively — it is a mandatory review item in Code Generation.

---

### SEC-U3.2: OBS Password Never Logged

Extends BR-U3-37. `ObsSettingsNotifier` must never log `state` as a whole object (it contains `password`). Log calls that reference `ObsSettings` must explicitly select only `host` and `port`.

**Verification**: Code review. `_$ObsSettingsToString` (generated by freezed) must not be used in any log statement.

---

### SEC-U3.3: BrowserSourceServer — All-Interface Binding with Token Authentication

`BrowserSourceServer` binds to `0.0.0.0` (all network interfaces) to support OBS running on a networked capture machine. Because the server is reachable beyond localhost, the `/captions` SSE endpoint is protected by a **one-time UUID token** generated at server start.

**Token rules**:
- A UUID token is generated via `Uuid().v4()` when `BrowserSourceServer.start()` is called.
- Requests to `GET /captions` are inspected for their remote address:
  - If `request.context['shelf.io.connection_info']` indicates the remote address is `127.0.0.1` or `::1`: token validation is **bypassed** (localhost traffic is trusted).
  - Otherwise: the request must include `?token={uuid}` matching the generated token. Requests without a valid token receive `401 Unauthorized`.
- The HTML page generated by `GET /` embeds the token in the JavaScript SSE client URL (`/captions?token={uuid}`).
- The token is stable for the lifetime of the server instance. A server `stop()` + `start()` generates a new token.

**Rationale**: The token protects remote access to the live caption stream. Localhost access is unrestricted because only the local user can reach it; adding a token for OBS on the same machine would require the user to copy a URL manually, degrading usability with no security gain.

**Verification**:
- Test: remote request to `/captions` without token → `401`
- Test: remote request to `/captions` with wrong token → `401`
- Test: remote request to `/captions` with correct token → `200 text/event-stream`
- Test: localhost request to `/captions` without token → `200 text/event-stream`

## 3. Reliability

### REL-U3.1: TranscriptDatabase — Corruption Recovery with User Notification

If the drift database file fails `PRAGMA integrity_check` at `TranscriptRepository` initialization:

1. Close the database connection.
2. Rename `transcripts.db` to `transcripts.db.corrupt` in the same directory.
3. Open a fresh empty database at `transcripts.db`.
4. Expose a `RepositoryEvent.corruption({required String corruptFilePath})` event via a `Stream<RepositoryEvent>` on `TranscriptRepository`. The UI layer observes this stream and presents a non-blocking notification to the user explaining that their transcript history was unreadable and has been backed up to `{corruptFilePath}`.

**No silent data loss**: the corrupt file is preserved so that a technically capable user can attempt manual SQLite recovery. The app continues normally with an empty database.

**Verification**: Test with a pre-corrupted SQLite fixture file. Assert the corrupt file is renamed, a fresh database is created, and the `corruption` event is emitted.

---

### REL-U3.2: BrowserSourceServer — Port-In-Use Error

If `BrowserSourceServer.start()` fails because the configured port is already bound, it throws `BrowserSourceStartException` with `reason: BrowserSourceStartFailureReason.portInUse` and the attempted `port` value.

`OutputTargetSettingsProvider` catches this exception and sets a `BrowserSourceError` state that the UI can observe to surface: "Port {N} is already in use. Change the port in Browser Source settings."

The user must manually change the port. There is no automatic port incrementing.

**Verification**: Test using a pre-bound `ServerSocket` on the target port before calling `start()`. Assert the exception is thrown with the correct reason and port.

---

### REL-U3.3: TranscriptWriterTarget — Immediate Segment Persistence (Supersedes BR-U3-09)

`TranscriptWriterTarget` writes each completed `TranscriptSegment` to `TranscriptRepository` **immediately** after finalization (either as a new segment or as a merge update). There is no periodic 30-second flush timer.

The final `SessionStateEvent(stopped)` flush remains, but its purpose is now only to:
- Call `repository.finalizeSession(sessionId, durationMs: ..., segmentCount: ...)` to update session metadata.
- Clear `_pendingMerge` state.

**Durability**: At most the **in-progress merge window** (up to 2s per source) can be lost on unexpected app kill. Any finalized segment that is no longer subject to merging has already been persisted.

**Implementation change from FD**: `_pendingSegments: List<TranscriptSegment>` is removed. `_lastFinalBySource: Map<String, TranscriptSegment>` is retained for the 2s merge window only. Segments are written via `repository.saveSegment()` immediately when either: (a) the merge window closes (>2s gap), or (b) a new session starts (forcing a flush of the open merge window).

**Verification**: Test that a final result triggers an immediate `repository.saveSegment()` call. Test that a second final result within 2s from the same source updates the existing persisted segment (upsert). Test that session stop triggers `finalizeSession()`.

---

### REL-U3.4: OBS Reconnection (Confirmed from FD)

The reconnection policy defined in BR-U3-24/25 (exponential backoff, 10-minute timeout) is confirmed as the reliability contract. No changes from FD.

**Verification**: Timer-based unit tests using `fake_async`. Test the full backoff schedule and the 10-minute cutoff.

## 4. Testing

### TEST-U3.1: Coverage Target — ≥90% Excluding CaptionOverlayTarget

Unit 3 targets **≥90% line coverage** across all new `zip_core` and `zip_broadcast` code. `CaptionOverlayTarget` and its `DesktopWindowService` platform implementation (`DesktopMultiWindowService`) are **excluded** from the coverage denominator. Coverage is measured with `flutter test --coverage`.

**Rationale**: `DesktopMultiWindow` platform channel calls require a native host runner and cannot be meaningfully exercised in unit tests. The abstraction boundary (TEST-U3.2) ensures all business logic above the platform layer is covered.

---

### TEST-U3.2: CaptionOverlayTarget — DesktopWindowService Abstraction

`CaptionOverlayTarget` does not call `desktop_multi_window` APIs directly. It depends on a `DesktopWindowService` abstract class:

```dart
abstract class DesktopWindowService {
  Future<int> createWindow(String arguments);
  Future<void> closeWindow(int windowId);
  Future<void> invokeMethod(int windowId, String method, dynamic arguments);
  bool get isSupported;
}
```

The production implementation (`DesktopMultiWindowService`) delegates to `desktop_multi_window`. In tests, `MockDesktopWindowService` (mocktail) is used. This pattern is consistent with the `SttEngine` abstraction in Unit 1.

`CaptionOverlayTarget` is tested for: `show()` on a fresh target, `show()` when already visible (update, not duplicate), `hide()`, `dispose()`, `onCaptionEvent()` routing (discarded when not visible, forwarded when visible), and the mobile/web no-op guard.

---

### TEST-U3.3: TranscriptRepository — Real In-Memory Drift Database

All `TranscriptRepository` tests use drift's in-memory database (`NativeDatabase.memory()`). FTS5 is exercised against drift's bundled SQLite, which includes FTS5 support. No file I/O occurs in tests.

`TranscriptWriterTarget` and `OnScreenCaptionTarget` tests use a `MockTranscriptRepository` (mocktail) to isolate them from database behavior.

---

### TEST-U3.4: Timer Control with fake_async

Tests involving the 2-second merge window in `TranscriptWriterTarget` use `fake_async` to advance time without real waits. OBS reconnection backoff tests (REL-U3.4) also use `fake_async` for the exponential delay schedule and 10-minute timeout.

---

### TEST-U3.5: BrowserSourceServer — HTTP and SSE Testing

`BrowserSourceServer` tests use a `shelf` `IOServer` bound to a test port (or `shelf_test`'s `TestClient` if available). Tests cover:

- `GET /` returns `200 text/html` with the generated template
- `GET /captions` without token from a simulated remote address → `401`
- `GET /captions` with correct token from remote address → `200 text/event-stream`
- `GET /captions` from `127.0.0.1` without token → `200 text/event-stream`
- `pushCaption()` broadcasts to connected clients
- 6th SSE client gets `503`
- Disconnected client is removed from the client list
- `start()` on an already-running server is a no-op

## 5. Maintainability

### MAINT-U3.1: Drift Schema Version 1 with Migration Scaffold

`TranscriptDatabase` is declared at `schemaVersion: 1`. The `MigrationStrategy` includes an empty `onUpgrade` switch scaffolded for future versions:

```dart
@override
MigrationStrategy get migration => MigrationStrategy(
  onCreate: (m) async {
    await m.createAll();
    // FTS5 virtual table + triggers via customStatement
  },
  onUpgrade: (m, from, to) async {
    switch (from) {
      // Version 2 migration will be added here
    }
  },
);
```

This ensures the migration path is documented and ready before the schema ever needs to change, reducing the risk of a missed migration in a future phase.

---

### MAINT-U3.2: Logger Naming Convention (Inherited)

All Unit 3 components use the `logging` package with the naming convention established in Units 1 and 2:

| Package | Logger name pattern | Example |
|---------|---------------------|---------|
| `zip_core` | `'zip_core.{ClassName}'` | `'zip_core.TranscriptRepository'` |
| `zip_broadcast` | `'zip_broadcast.{ClassName}'` | `'zip_broadcast.ObsWebSocketTarget'` |

---

### MAINT-U3.3: Transcript Retention Policy Deferred

No automated retention policy is implemented in Unit 3. Manual deletion via `TranscriptRepository.deleteSession()` is the only mechanism. A configurable retention policy (by session count or age) is a post-launch feature item.
